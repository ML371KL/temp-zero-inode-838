# Уведомления в Telegram

Бот присылает сообщение, когда состояние панели действительно изменилось: «как было → как стало»
плюс короткий комментарий о смысле и вероятных последствиях. Один бот обслуживает обе панели.

## Что считается событием

| Тип | Когда | Пример |
|---|---|---|
| 🎯 целевая доля | изменилась предписанная доля капитала | `80% → 5%` |
| ⚖️ вердикт | сменился общий вывод панели | `ДЕРЖАТЬ·ДОКУПАТЬ → ДЕРЖАТЬ` |
| 🔔 детектор | сработал, перешёл в наблюдение или успокоился | `спокоен → СРАБОТАЛ` |
| 🚦 смена зоны | показатель сменил зону или вклад в балл | `«0…+1,5», балл +1 → «−1,5…0», балл 0` |
| 📊 новые данные | первоисточник опубликовал релиз И значение изменилось | одно сообщение на публикацию, все её карточки внутри |
| ♻️ ревизия | первоисточник переписал уже опубликованные данные | `27.05.2026: 9,463·10^20 → 9,404·10^20 (−0,63%)` |

**Про ревизии отдельно.** Собственный алерт панели («источник переписал N строк») в рассылку НЕ
идёт: он несёт только хеши и счётчики и не отвечает на единственный важный вопрос — что именно и
на сколько изменилось. Вместо этого запоминаются последние 150 точек ряда каждой карточки, и
ревизия ловится сравнением одних и тех же меток времени: сообщение называет дату, старое значение,
новое и процент. Точки от последней запомненной и новее не сравниваются — последняя точка суток
ещё формируется, её движение это рынок, а не пересмотр истории. Одна переписанная точка
первоисточника обычно двигает несколько карточек сразу, поэтому ревизии группируются по периоду, а
карточки с одинаковыми числами склеиваются в одну строку.

**Чего НЕ бывает.** У непрерывных рыночных фидов (споты, деривативы, пеги, комиссии мемпула,
котировки BIZD/ширины) «значение изменилось» — не событие: они меняются каждую секунду. Для них
остаётся только смена зоны или балла. На BTC-панели такие карточки распознаются автоматически по
возрасту наблюдения (моложе 6 часов = живой фид), на макро-панели — таблицей `MACRO_CADENCE`
в `scripts/notify.mjs`.

Релиз без изменения значения молчит: сообщение уходит, только когда цифра действительно другая.

## Установка (5 минут)

1. Создать бота: написать [@BotFather](https://t.me/BotFather) → `/newbot` → получить токен вида
   `123456:AA...`.
2. Написать своему боту любое сообщение (иначе он не имеет права писать первым), затем открыть
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и взять оттуда `chat.id`.
3. В репозитории: **Settings → Secrets and variables → Actions → New repository secret**
   - `TELEGRAM_BOT_TOKEN` — токен из шага 1;
   - `TELEGRAM_CHAT_ID` — id из шага 2;
   - `OPENROUTER_KEY` — необязательно: с ним комментарии пишет модель, без него — шаблон.
4. Необязательно: переменная `NOTIFY_MODEL` (**Variables**, не Secrets) — модель комментатора.

Готово. Уведомления пойдут после следующего штатного прогона снимка.

## Проверка связи

Не дожидаясь первого настоящего изменения: вкладка **Actions** → слева **Уведомления в Telegram**
→ кнопка **Run workflow** → галочка **«Проверка связи»** → **Run workflow**. Придёт одно сообщение
с текущим состоянием панели. Пинг НЕ трогает состояние рассылки — обычный ход не сбивается.

Первый обычный прогон после установки ничего не пришлёт: он только фиксирует базу сравнения.
Иначе бот вывалил бы разом состояние всех карточек.

## Как это устроено

- Отдельный workflow `notify.yml`, запускается по завершении прогона снимка (`workflow_run`) —
  собственный GitHub-cron в этих репозиториях ненадёжен, а снимок дёргается внешним будильником.
- **BTC-панель** читает `docs/snapshot.json`: там уже посчитаны карточки, баллы и детекторы.
- **Макро-панель** считает карточки в браузере, поэтому состояние снимается headless-прогоном
  опубликованной страницы (`state.settled === true`, затем проекция `IND` + `state.data`).
  Второй копии логики скоринга на сервере СОЗНАТЕЛЬНО нет — она бы неизбежно разошлась с боевой.
- Состояние «что уже отправлено» живёт в Actions Cache. Потеря кэша безопасна: скрипт зафиксирует
  базу заново и промолчит — худший исход это пропуск уведомления, а не лавина сообщений.
- Уведомления живут СНАРУЖИ решающего контура: читают уже опубликованное состояние, ничего не
  пишут ни в снимок, ни в решение. Отказ бота не может ни изменить вердикт, ни заморозить сайт.
  Поэтому `notify-test.mjs` не входит в `npm run check`, а гоняется внутри самого `notify.yml`.

## Модель комментатора: только бесплатная

По умолчанию используется `nvidia/nemotron-3-ultra-550b-a55b:free` — та же модель, что уже судит
новости на макро-панели (в каталоге OpenRouter на 24.07.2026: цена `0 / 0`, контекст 1M, максимум
вывода 65 536 токенов — с запасом на наши ≤4000).

Это не «так сложилось», а закреплено кодом: если `NOTIFY_MODEL` указывает на модель, чей id **не
оканчивается на `:free`**, запрос вообще не уходит в сеть — в лог пишется причина, комментарии
берутся из шаблона. Платная модель требует явного `NOTIFY_ALLOW_PAID=1`. Одна опечатка в переменной
не должна начать жечь деньги на каждом из сотни суточных прогонов.

**Лимиты бесплатного уровня OpenRouter** (по документации на 24.07.2026): 20 запросов в минуту и
50 запросов в сутки, а при пополнении счёта хотя бы на $10 когда-либо — 1000 в сутки. Квота общая
с судьёй новостей макро-панели. Чтобы её не жечь, комментатор делает **один запрос на прогон** на
все события сразу, а не по запросу на сообщение. При исчерпании лимита приходит `429`, и сообщения
уходят с шаблонными комментариями — уведомление не теряется.

## Настройка потока

| Переменная | Смысл | По умолчанию |
|---|---|---|
| `NOTIFY_DRY_RUN=1` | печатать сообщения в лог, ничего не отправлять | выкл (без токена — включается сам) |
| `NOTIFY_MAX` | предохранитель: больше N событий за прогон — отправятся первые N по важности | 40 |
| `NOTIFY_GAP_MS` | пауза между сообщениями (лимит Telegram ~20/мин в чат) | 3500 |
| `NOTIFY_MODEL` | модель комментатора OpenRouter; не-`:free` требует `NOTIFY_ALLOW_PAID=1` | бесплатная nemotron |

Проверить локально, ничего не отправляя:

```bash
NOTIFY_DRY_RUN=1 NOTIFY_STATE=.notify/state.json node scripts/notify.mjs
```

## Ожидаемый объём

В обычные сутки — единицы сообщений. В день, когда сходятся релиз занятости, H.4.1, ETF-потоки и
ончейн-пакет, — до полутора-двух десятков. Проверено на реальном интервале 23–24 июля 2026 (внутри
была смена режима BTC-панели с доли 80% на 5%): 22 сообщения за 32 часа.

Если станет шумно, самый эффективный тумблер — отключить тип `release` в `KIND_ORDER`: тогда
останутся только смены зон, вердиктов, детекторов и ревизии, то есть события, меняющие вывод.
